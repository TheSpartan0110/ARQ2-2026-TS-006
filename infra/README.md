# Infrastructure (Wave 2 - Step 1)

Base platform defined by `docs/spec.md` and ADRs 001-006: PostgreSQL, Redis, RabbitMQ, Mailpit and the
observability stack (OpenTelemetry Collector, Prometheus, Loki, Tempo, Grafana).
Business services are added on top of this in later steps.

## Run

```bash
docker compose up -d          # optional first: cp .env.example .env
docker compose ps             # wait until postgres, redis and rabbitmq are "healthy"
./infra/smoke-test.sh         # automatic verification
docker compose down           # stop (keeps data)   |   docker compose down -v  -> also wipe data
```

> PostgreSQL only runs `init-schemas.sh` on an **empty** volume. After changing it, run `docker compose down -v`.

## Design decisions

| Piece | Decision | Why |
|---|---|---|
| PostgreSQL | 1 instance, 7 schemas, 1 role per schema; the init script fails if a role can reach another schema | ADR 004; data ownership enforced by the database |
| Redis | No persistence, `allkeys-lru`, 256 MB | ADR 002: cache only, PostgreSQL is the source of truth |
| RabbitMQ topology | Loaded from `definitions.json` (generated by `generate_definitions.py`) | Queues, DLQs and permissions are reproducible and reviewable |
| Retry | `<queue>.retry.5s/30s/120s` with TTL, dead-lettering back to the source queue | Spec 4.3 item 4: retries after 5, 30 and 120 s, then DLQ |
| RabbitMQ users | One per service, least privilege (read only its queue) | Spec 4.2.5 |
| Logs | Services write JSON to stdout; Grafana Alloy reads the eight services' container logs through the Docker API and labels them by `service` and `level` | Spec 6.1; no log agent inside services |
| Traces | Services -> Collector (OTLP) -> Tempo, 100% sampling | Spec 6.3 |
| Metrics | Prometheus scrapes `<service>:8081/actuator/prometheus`; adds the `service` label itself | Spec 6.1 / 6.4 |
| Grafana | Login required; datasources and dashboards provisioned as code; Loki <-> Tempo linked by `traceId` | Spec 6.1 / 6.5 |
| Dashboards | Folder *EatsNow*: Order flow, Messaging, Payments, Catalog, Service health (Spec 6.4), Load tests (k6 runs) and Infrastructure; JSON in `infra/grafana/dashboards/`, read-only in the UI | Spec 6.4 / 6.7 |

### Retry flow (per queue)

```
queue --nack(requeue=false)--> DLX ---> <queue>.dlq              (poison / retries exhausted)
consumer --publish--> eatsnow.retry.v1 --> <queue>.retry.5s --(TTL)--> default exchange --> queue
```
The consumer counts attempts (header `x-death` or its own) and chooses 5s, 30s, 120s, then the DLQ.

## Plugging a service in

1. Add it to `docker-compose.yml` (copy `orders`) with its own `DB_URL`/`DB_USER` and RabbitMQ credentials.
2. Set `spring.application.name`: it becomes the trace `service.name` and the `service` field of every log line.
3. Expose Actuator on **management port 8081**; Prometheus discovers `<service>:8081` by Docker DNS name.
4. Add `micrometer-tracing-bridge-otel` and `opentelemetry-exporter-otlp`, and set
   `management.otlp.tracing.endpoint=http://otel-collector:4318/v1/traces` (Spring Boot does **not** read `OTEL_*`
   variables; those only work with the Java agent).
5. Do **not** add a `service` tag to metrics: Prometheus adds it at scrape time.
6. `logback-spring.xml` must emit JSON with `"service": "<name>"` and the `<arguments/>` provider (so
   `kv("operation", ...)` becomes a field). Without the `service` field the line has no `service` label in Loki.

## Known caveats

- `*.sh` and config files must keep LF line endings (enforced by `.gitattributes`).
- Alloy reads logs through `/var/run/docker.sock`, which works on Docker Desktop (Windows, macOS) and Linux. Reading `/var/lib/docker/containers` instead ships nothing on Docker Desktop: that folder lives inside Docker's VM.
- Alert rules are evaluated by Prometheus (Prometheus UI -> Alerts). There is no Alertmanager yet; Grafana alerting can be wired in step 4.6.
- Several metrics in `alerts.yml` and the dashboards only appear once the services publish them (counters after their first event).
